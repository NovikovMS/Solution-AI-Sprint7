# Полная постановка для трёх инициатив (раздел 1 паспорта)

Постановка по структуре: **операция и модальность → выход модели против бизнес-выхода → источник правильного ответа**. На каждом звене цепочки проверяем, нужна ли там модель или достаточно обычной программы.

---

## Инициатива № 1 — Выявление подозрительных операций (флагман, гибрид)

### Операция и модальность

- **Операция (единица обработки):** одна операция по счёту клиента (платёж) с атрибутами — сумма, назначение платежа (свободный текст), контрагент, ОКВЭД, дата, канал; плюс агрегаты по клиенту и контрагенту за окно (обороты, частота, доля транзитных паттернов, разбивка платежей под пороги).
- **Модальность:** табличные признаки + свободный текст назначения платежа. Документов и изображений на входе нет. Текст назначения обрабатывается как дополнение к табличным признакам (эмбеддинги/ключевые слова), а не как самостоятельная задача.
- **Режим:** асинхронная пакетная обработка потока операций (режим ранжирования), не синхронный ответ на каждый платёж. Модель пересчитывает приоритеты очереди для финмониторинга и не блокирует платёж.

### Выход модели против бизнес-выхода

- **Выход модели:** ранг/скор «степени подозрительности» операции + топ-факторы, повлиявшие на оценку (для объяснимости). Это **не** вердикт «схема/не схема».
- **Бизнес-выход:** переупорядоченная очередь операций для ручной проверки финмониторингом. Детерминированные пороговые правила продолжают работать параллельно и помечают операции независимо. Решение об углублённом расследовании, отказе в проведении или снятии пометки принимает сотрудник по результатам разбора. Цель — увеличить долю действительно подозрительных операций в разобранной выборке и сократить время до разбора критичных случаев, не отменяя обязательную процедуру контроля.
- **Уровень автоматизации:** модель только рекомендует порядок; вердикт и действие — за человеком и правилами.

### Источник правильного ответа

Готовой разметки «схема/не схема» нет. Доступны три следа разной надёжности, ни один не эталон:

1. Отметка «эскалировано на расследование» (~400/мес) — отражает срабатывания правил и решения операторов, а не подтверждённую схему.
2. Исход расследования — чаще «ничего», часть — отказ в операции, единицы — формально подтверждены.
3. Формально подтверждённые случаи — единицы, появляются спустя месяцы.

Непроверенная операция не равна чистой: очередь формировалась пороговыми правилами и внешними сигналами (смещение отбора).

**Развилка получения сигнала:**

- **Путь A — слабые метки + постановка без учителя:** обучение/ранжирование на слабых следах с честной оговоркой, что модель воспроизводит логику существующих правил; целевая постановка — ранжирование на ручную проверку, а не вердикт. Самый дешёвый и быстрый, но ограничен в качестве.
- **Путь B — разметка силами финмониторинга по гайдлайну:** целевая разметка выборки с оценкой согласованности разметчиков (κ Кохена/Флейсса). Дороже и дольше, даёт эталон.
- **Путь C — вероятностная контрольная выборка:** случайная/стратифицированная по сегментам и суммам выборка из **всего** потока (не только из очереди), размеченная экспертами, — даёт несмещённую оценку того, что происходит в непроверяемой части потока, и служит приёмочным набором.

**Рекомендация для постановки:** гибрид путей A+C — модель ранжирует очередь (путь A), а качество измеряется на постоянной вероятностной контрольной выборке (путь C); разметка накапливается из двух источников — разобранной приоритетной очереди и контрольной выборки. Брать разметку только из очереди нельзя — это создаёт новое смещение собственного производства.

## Инициатива № 2 — Распознавание и оцифровка сканов документов кредитной заявки (гибрид)

### Операция и модальность

- **Операция (единица обработки):** один документ из пакета кредитной заявки (выписка по счёту в другом банке, бухгалтерская отчётность, договор с контрагентом, справка) в форматах Excel, PDF-скан, выгрузка из бухгалтерской системы, фотография с телефона.
- **Модальность:** изображения (сканы/фото) + структурированные/полуструктурированные файлы (Excel, выгрузки). Для сканов и фото нужен OCR, затем разбор структуры документа и извлечение именованных полей и табличных значений.
- **Режим:** асинхронная обработка пакета документов по заявке (не синхронный ответ в момент загрузки); результат предзаполняет карточку заявки для андеррайтера.

### Выход модели против бизнес-выхода

- **Выход модели:** извлечённый набор полей документа с координатами/цитатами-источниками (ссылка на фрагмент документа) и оценкой уверенности по каждому полю; класс документа (баланс/ОФР/выписка/справка/договор).
- **Бизнес-выход:** предзаполненная и провалидированная карточка заявки для андеррайтера, с пометками расхождений и полей, требующих подтверждения. Андеррайтер подтверждает критичные поля и принимает решение по кредиту. Цель — сократить время разбора пакета с ~1,5 часов на заявку и снизить долю ручного ввода.
- **Уровень автоматизации:** модель извлекает и предзаполняет; детерминированная валидация сверяет значения (внутри документа, между документами, с внешними источниками); человек подтверждает критичные поля и итоговое решение. Автозаполнение без подтверждения недопустимо для полей, влияющих на решение.

### Источник правильного ответа

- **Эталон для верификации извлечения:** структурированные выгрузки из бухгалтерских систем и структурированные банковские выписки — по ним можно сверять извлечённые значения как по готовому правильному ответу. Для сканов, где эталона нет, — разметка полей экспертами (андеррайтерами) на контрольной выборке документов.
- **Приёмочный набор:** выборка документов разных типов и форматов (Excel, PDF-скан, фото), с разметкой эталонных значений полей; стратифицирована по типу документа, качеству скана, формату.
- **Сигнал качества:** точность извлечения полей (точность/полнота/F1 по полям), доля документов, потребовавших ручной правки, доля критичных полей с высокой уверенностью. Метрика «модель даёт 92 % точности» без источника недопустима — пороги обосновываются долей ручной правки, которую готов принять андеррайтер.

## Инициатива № 8 — Предсказание оттока клиентов (ML-кандидат)

### Операция и модальность

- **Операция (единица обработки):** клиент-юрлицо/ИП на момент оценки с агрегатами поведения за окно (обороты по счетам, частота и сумма операций, эквайринг, кредитная нагрузка, жалобы, приостановки и их исход, срок в банке, тарифный план, ОКВЭД).
- **Модальность:** табличные признаки (агрегаты по клиенту за скользящие окна). Текста и документов на входе нет.
- **Режим:** пакетный регулярный пересчёт (раз в неделю/месяц) по всем активным клиентам; не синхронный ответ на операцию.

### Выход модели против бизнес-выхода

- **Выход модели:** оценка вероятности оттока клиента на горизонте (1–3 месяца) + топ-факторы (для объяснимости и выбора меры удержания). Это **не** решение «блокировать/не блокировать» и не действие над клиентом.
- **Бизнес-выход:** ранжированный список клиентов группы риска для proactive-удержания (персональный менеджер, компенсация за ложную приостановку, предложение); мера удержания подбирается по причине оттока (одна из топ-факторов). Цель — снизить отток клиентов, теряемых после ложных приостановок и жалоб, и сохранить комиссии/обороты.
- **Уровень автоматизации:** модель только рекомендует; контакт и предложение — за человеком (персональным менеджером). Полностью автоматическое действие над клиентом не допускается (риск раздражения лояльных клиентов).

### Источник правильного ответа

- **Метка оттока:** наблюдаема по факту закрытия счёта/падения активности ниже порога за период. Источник — история операций за несколько лет.
- **Порог факта оттока и горизонт прогноза** — параметры, требующие уточнения у бизнеса (см. уточняющий вопрос в триаже): что считать «ушёл» (закрытие счёта / падение оборотов ниже X% на N месяцев) и на каком горизонте предсказывать.
- **Смещение отбора:** непроверяемое — метка формируется по всему потоку клиентов, а не по выборке правил. Репрезентативность — есть.
- **Приёмочный набор:** исторические клиенты с известным исходом (ушёл/остался), стратифицированные по сегменту, сроку, тарифу; временной split (train на прошлом, test на более позднем периоде) для проверки устойчивости во времени. Метрики: ROC-AUC/PR-AUC, precision@k (доля действительно ушедших в топ-k, на кого тратим усилия удержания), recall@k. Пороги — из экономики: стоимость контакта × доля успешного удержания против ценности сохранённого клиента.
