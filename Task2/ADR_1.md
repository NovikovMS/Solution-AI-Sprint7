# ADR — Выявление подозрительных операций (флагман)

Сквозной документ по флагману, дополняется по мере работы. Прежние решения не стираются, а помечаются как пересмотренные с причиной. Здесь — предварительное решение по размещению (v0.1) и выбор модели (v0.2). Разделы 2–5 паспорта — в `passport_1.md`.

---

## v0.1 — Предварительное решение по размещению

### Контекст

Банк для МСБ.

- **Поток:** 20–25 млн операций по счетам в месяц.
- **Финмониторинг:** 25 сотрудников разбирают ~10 тыс. из ~35 тыс. помеченных — очередь растёт, приоритет крупным суммам.
- **Цена обеих ошибок высока:**
  - пропущенная схема → предписания надзора (два за прошлый год);
  - ложная блокировка → ~600 приостановок/мес, 120 жалоб, отток.
- **AML — обязанность банка:** решение встраивается в правила внутреннего контроля и не отменяет процедуру.
- **Разметка:** готовой разметки «схема/не схема» нет — есть три слабых следа, ни один из них не эталон. Непроверенная операция не равна чистой: очередь формировали правила, отсюда смещение отбора.

Постановка — приоритизация очереди ручной проверки: модель меняет порядок очереди, вердикт и блокировка остаются за детерминированными правилами и человеком.

### Поток данных

Операция с атрибутами + агрегаты по клиенту/контрагенту за окно → модель → скор/ранг → переупорядоченная очередь.

- **Атрибуты операции:** сумма, назначение платежа (свободный текст), контрагент, ОКВЭД, дата, канал.
- **Агрегаты по клиенту/контрагенту за окно:** обороты, частота, доля транзитных паттернов, разбивка платежей под пороги.
- **На входе — чувствительные данные:**
  - банковская тайна;
  - ПДн (клиенты-юрлица, но среди них ИП; по сделкам — поручители-физлица).

### Класс данных (подтверждает DPO)

- Банковская тайна (сведения об операциях и счетах).
- ПДн клиентов-юрлиц, представителей, поручителей-физлиц.
- Специальная категория не применима (нет сведений о здоровье и т.п.), но состав данных чувствительный.

### Жёсткие ограничения

- **AML:** решение встраивается в правила внутреннего контроля, не отменяет процедуру выявления и фиксирования. Модель не выносит вердикт о блокировке — только ранжирует очередь.
- **Право:** чувствительные данные (банковская тайна, ПДн) — передачу за контур и размещение определяют комплаенс, DPO и юристы, а не архитектор. До их ответа варианты с передачей данных за контур не допускаются.
- **Воспроизводимость:** для регуляторного разбора нужна воспроизводимость ответа — закрепление версии модели или регрессионный прогон при обновлении.
- **Смещение отбора (ограничение на постановку, не на размещение):** обучение на срабатываниях правил воспроизводит их логику. Поэтому постановка — ранжирование на слабых метках с честной оговоркой, а не классификация «схема/не схема».

### Рассмотренные варианты размещения

| Вариант | Пилот | Прод |
|---|---|---|
| Публичный API | Допустимо: передаём только обезличенные агрегаты, без ПДн | Отклонён: банковская тайна, регион хранения не гарантирован, обучение провайдера на наших данных |
| Выделенный контур провайдера | Допустимо | Кандидат — но только для разбора назначения платежа, если для него возьмём LLM |
| Self-hosting в облаке (свой контур) | Кандидат | Кандидат |
| On-prem (свой ЦОД) | Допустимо | Кандидат |
| Гибрид по звеньям | — | Кандидат: скоринг операции считаем on-prem, а разбор назначения платежа выносим в выделенный контур |

### Решение

- **Пилот — разворачиваем модель сами, в своём контуре в облаке.** Данные не покидают периметр: ПДн и банковская тайна наружу не уходят. Модель работает на признаках операции, ей достаточно CPU, GPU не нужен — поэтому вариант дешёвый. On-prem тоже подошёл бы, но его контур ещё не готов, а облако при той же изоляции данных запускается быстрее.
- **Прод — не выбран окончательно.** Кандидаты: on-prem целиком либо гибрид, где скоринг операции считается on-prem, а разбор назначения платежа выносится в выделенный контур провайдера (это нужно, только если для текста возьмём LLM). Выбираем после замера реальной нагрузки и выбора модели. Публичный API для прод-потока отклонён по жёстким ограничениям.

### Допущения

- Нагрузка в проде неизвестна. Всего операций 20–25 млн в месяц, но сколько из них реально дойдёт до модели, зависит от того, как отфильтруют поток правила.
- Эксплуатировать модель своими силами команда пока не готова: круглосуточного дежурства по ML нет, GPU не закуплены.
- Для пилота достаточно обезличенных агрегатов. Для прода вопрос о передаче назначения платежа за контур остаётся открытым — ответ за комплаенсом и DPO.

### Риски

- Смещение отбора: модель на слабых метках воспроизводит логику правил — честная оговорка, качество мерим на контрольной выборке (путь C).
- Деградация на новых сегментах (напр. селлеры маркетплейсов) — не покрыты обучением.
- Lock-in при использовании API/выделенного контура — смягчается адаптером и планом выхода.
- Изменение закона/регуляторики по трансграничной передаче и локализации.

### План выхода от вендора

Адаптер перед моделью (единый выходной контракт). Миграция на второго поставщика/другую модель — оценивается в N недель. При self-hosting — миграция на другую open-weight/свою модель, ниже зависимость, выше операционная нагрузка.

### Триггеры пересмотра

- Рост нагрузки вне расчётной.
- Изменение цен/SLA вендора.
- Изменение закона/регуляторики (трансграничная передача, локализация).
- Деградация на новом сегменте, не покрытом обучением.
- precision@N ≤ baseline на пилоте → пересмотр постановки (возможно отказ от ML в этом звене).

## v0.2 — Выбор модели

### Статус

Предварительный шортлист кандидатов и процедура окончательного выбора. До прогона на приёмочной выборке решение считается предварительным.

### Контекст

Постановка — ранжирование операций по признакам операции и клиента, плюс назначение платежа, которое клиент пишет свободным текстом.

Модель нужна только в одном звене — оценить подозрительность операции. Всё остальное в конвейере детерминировано: пороговые правила помечают операции, сортировка выстраивает очередь, разбор ведёт человек. Поэтому модель выбираем под это звено, а не под инициативу целиком.

### Жёсткие ограничения (на модель)

- **Воспроизводимость:** для регуляторного разбора нужно уметь повторить оценку — закрепляем версию модели либо прогоняем регрессионный набор при каждом обновлении.
- **Задержка:** режим пакетный, поэтому сейчас не ограничивает. Может стать ограничением при росте объёма.
- **Поведение на незнакомых данных:** по операции нового клиента или контрагента без истории модель должна отдавать низкую оценку и уходить в фолбэк, а не выдавать уверенный скор на пустых признаках.
- **Размещение:** модель должна запускаться в своём контуре или on-prem и обходиться без GPU. LLM в роли классификатора не рассматриваем: она склонна к галлюцинациям, а вердикт от модели здесь и не требуется — нужна только оценка для сортировки очереди.

### Шортлист кандидатов

Кандидаты сгруппированы по тому, что меняется в архитектуре: где звено исполняется, что пересекает границу контура, как формируется стоимость и какой риск мы принимаем. Конкретный алгоритм внутри группы — решение DS-команды по результатам приёмочного прогона, и на архитектуру оно не влияет.

| Кандидат | Где исполняется | Плюсы | Минусы |
|---|---|---|---|
| Ансамбль деревьев на признаках операции, назначение платежа разбирается по ключевым словам (TF-IDF). Внутри семейства — градиентный бустинг, случайный лес и подобные | Свой контур в облаке или on-prem | Зрелая технология, даёт топ-факторы для объяснения оценки, работает на CPU без GPU | Назначение платежа разбирается только по словам, смысл редких формулировок теряется |
| Линейная модель (логистическая регрессия) на тех же признаках | Свой контур или on-prem | Полностью интерпретируема, дёшева, годится как точка отсчёта для сравнения | Хуже улавливает сложные сочетания признаков |
| Тот же ансамбль плюс эмбеддинги назначения платежа как дополнительный признак | Свой контур или on-prem | Улавливает смысл редких формулировок | Добавляет в конвейер отдельное звено и требует больше ресурсов |
| LLM разбирает назначение платежа: извлекает из текста признаки, вердикт не выносит | Выделенный контур провайдера | Лучше всех работает со свободным текстом | Галлюцинации, плата за токены на нашем объёме, зависимость от вендора |

### Процедура окончательного выбора

1. **Диагностический отсев** (12–20 операций):
   - транзит, обнал, дробление;
   - редкая формулировка назначения;
   - операция нового клиента (без истории);
   - операция с пропусками признаков;
   - операция с противоречивыми признаками.
   
   Проверка: честное «не знаю»/низкий скор на операции без истории, падение скора на противоречивых, стабильность формата.
2. **Приёмочный прогон** на вероятностной контрольной выборке (путь C) из всего потока, стратифицированной по сегментам и суммам. Метрики: precision@N, recall@N, сумма предотвращённых схем в top-N.
3. **Пороги** берём из экономики: сколько стоит разбор одной операции против того, во сколько обходится пропущенная схема. Приёмочный порог — precision@N не ниже текущего уровня плюс согласованная с бизнесом прибавка. Публичный рейтинг модели источником порога не является.
4. **Что считаем провалом на конкретном сценарии:**
   - модель уверенно скорит операцию, по которой нет признаков, — кандидат отклоняем;
   - модель не справляется с операциями без истории — оставляем для них детерминированные правила;
   - модель теряет редкие формулировки назначения платежа — добавляем эмбеддинги или размечаем редкие случаи вручную.
5. **При каком результате меняем решение:**
   - precision@N не превысил текущий уровень — ML в этом звене не нужен, закрываем;
   - precision@N вырос на согласованную величину — подтверждаем кандидата и идём в целевой прод, параллельно запуская программу разметки (путь B).

### Решение

Предварительный кандидат — **ансамбль деревьев на признаках операции, назначение платежа разбираем по ключевым словам**. Размещение: свой контур в облаке на пилоте, on-prem в проде.

Какой именно алгоритм взять внутри семейства — градиентный бустинг, случайный лес или другой — определяет DS-команда на приёмочном прогоне. Для архитектуры они равнозначны: одинаково размещаются, одинаково считаются на CPU, одинаково дают факторы для объяснения оценки. Фиксировать этот выбор в ADR значило бы принять за команду решение, которое проверяется замером.

Условие принятия — подтверждение порогов на вероятностной контрольной выборке. До этого решение остаётся предварительным.

### Ценой чего

Назначение платежа разбирается только по словам, поэтому часть редких формулировок модель не уловит. Идём на это сознательно: такие операции остаются в общем потоке и попадают к человеку обычным порядком, а поднять их в очереди можно позже, добавив эмбеддинги. Чего мы не готовы принять — уверенной оценки на операции, по которой признаков нет; такие случаи ловит валидатор и уводит в фолбэк.

### Отклонено

- **LLM в роли классификатора** — склонна к галлюцинациям, дорога на нашем объёме и привязывает к вендору, а вердикт от модели здесь не требуется.
- **Крупная проприетарная модель через публичный API** — пришлось бы выносить банковскую тайну и ПДн за контур, к тому же провайдер не закрепляет версию, и оценку нельзя воспроизвести при разборе.

### Размещение прода (предварительное)

Скоринг операции — on-prem. Если для разбора назначения платежа возьмём эмбеддинги или LLM, это звено уходит в выделенный контур провайдера. Окончательно подтверждается вместе с кандидатом после приёмочного прогона.

### Допущение

Качество подтверждено только диагностическим отсевом на 12–20 операциях. До прода — прогон на вероятностной контрольной выборке (путь C).

### Зафиксированные требования

- Закрепить версию модели либо прогонять регрессионный набор при каждом обновлении.
- Не допускать уверенных оценок на операциях без признаков — доля таких случаев должна быть нулевой.
- Отдельно отслеживать, сколько операций с редкими формулировками назначения модель не поднимает в очередь.
- Проверять формат и диапазон оценки на выходе.
- Держать фолбэк на детерминированные правила — для операций без истории и на случай деградации модели.
