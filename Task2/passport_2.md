# Паспорт инициативы № 2 — Распознавание и оцифровка сканов документов кредитной заявки

Разделы 2–5 паспорта. Раздел 0 (канвас) и раздел 1 (триаж) — в `Task1/`.

---

## Раздел 2. Постановка

- **Бизнес-цель:** сократить время разбора пакета документов по кредитной заявке (сейчас ~1,5 ч/заявка) за счёт предзаполнения и валидации полей карточки заявки для андеррайтера.
- **Объект решения:** один документ из пакета кредитной заявки (выписка по счёту в другом банке, бухгалтерская отчётность, договор с контрагентом, справка) в форматах Excel, PDF-скан, выгрузка из бухгалтерской системы, фото с телефона.
- **Входные данные:** изображения (сканы/фото) + структурированные/полуструктурированные файлы (Excel, выгрузки). Для сканов и фото нужен OCR, затем разбор структуры и извлечение именованных полей и табличных значений.
- **Операция:** извлечение структуры — превратить документ в набор полей с привязкой к месту в исходнике. Дополнительно — классификация типа документа: баланс, отчёт о финансовых результатах, выписка, справка или договор.
- **Результат модели:** извлечённый набор полей с координатами/цитатами-источниками и оценкой уверенности по каждому полю; класс документа.
- **Результат для бизнеса:** предзаполненная и провалидированная карточка заявки с пометками расхождений и полей, требующих подтверждения. Андеррайтер подтверждает критичные поля и принимает решение по кредиту.
- **Дальнейшее действие:** андеррайтер проверяет пометки расхождений, подтверждает критичные поля, выносит решение.
- **Источник правильного ответа:** эталон для верификации — структурированные выгрузки из бухгалтерских систем и структурированные банковские выписки (готовый правильный ответ). Для сканов, где эталона нет, — разметка полей экспертами (андеррайтерами) на контрольной выборке.
- **Роль правил и человека:** модель извлекает и предзаполняет; детерминированная валидация сверяет значения (внутри документа, между документами, с внешними источниками); человек подтверждает критичные поля и итоговое решение. Автозаполнение без подтверждения недопустимо для полей, влияющих на решение.
- **Открытые вопросы:** нужна ли только оцифровка полей или также семантическая сверка документов между собой на противоречия (вопрос бизнесу); какие поля считать критичными (с андеррайтингом).

## Раздел 3. Качество

- **Бизнес-действие:** андеррайтер получает предзаполненную карточку заявки и проверяет только пометки расхождений и критичные поля, а не вводит всё вручную.
- **Положительный класс:** поле извлечено верно (совпало с эталоном). На уровне документа — документ превратился в запись с верными значениями всех критичных полей.
- **Метрика, связанная с решением:** точность извлечения полей — precision/recall/F1 по каждому полю отдельно (разные поля имеют разную цену ошибки). Доля документов, потребовавших ручной правки. Доля критичных полей с высокой уверенностью. **Не** «модель даёт 92% точности» без источника.
- **Baseline:** текущий ручной ввод андеррайтером (1,5 ч/заявка). Сравнение — доля полей, которые андеррайтер не правит вручную, и сэкономленное время на заявку.
- **Выборка для проверки:** выборка документов разных типов и форматов (Excel, PDF-скан, фото), с разметкой эталонных значений полей; стратифицирована по типу документа, качеству скана, формату. Для сканов эталон — ручная разметка андеррайтеров; для структурированных выгрузок — готовый эталон.
- **Рабочая точка:** порог уверенности поля, выше которого поле идёт в карточку без подтверждения; ниже — пометка «требует подтверждения». Порог — из доли ручной правки, которую готов принять андеррайтер.
- **Показатели в рабочей точке:** F1 по полям, доля автозаполненных полей, доля полей на подтверждение, доля документов без правки, сэкономленное время на заявку.
- **Стоимость ошибок:** FP — неверное значение в карточке, которое андеррайтер правит (цена — время правки); FN — пропущенное поле, которое андеррайтер вводит сам или запрашивает у клиента (задержка). Критичное поле (сумма выручки, долг) с ошибкой → неверное кредитное решение, поэтому такие поля всегда на подтверждение.
- **Guardrails:** ни одно критичное поле не должно попасть в карточку без подтверждения андеррайтера — независимо от того, насколько модель в нём уверена. Кроме того, доля документов, потребовавших полной ручной правки, не должна вырасти, а время на заявку — увеличиться.
- **Допущения и открытые вопросы:** порог уверенности и список критичных полей — с андеррайтингом; доля правки, которую готов принять андеррайтер, — замеряется на пилоте.

## Раздел 4. Данные

| Поле | Значение |
|------|---------|
| Решение | Предзаполнение и валидация карточки кредитной заявки |
| Объект и гранулярность | Один документ из пакета заявки.<br><br>Поля — отдельные единицы оценки |
| Источник и владелец | Кредитный конвейер (сами документы), андеррайтинг (разметка и эталонные значения), бухгалтерские системы клиентов (структурированные выгрузки как готовый эталон) |
| Сигнал / источник правильного ответа | Структурированные выгрузки из бухгалтерских систем и структурированные банковские выписки — готовый эталон. Для сканов — ручная разметка андеррайтеров |
| Доступность признаков после запуска | Документ поступает в момент заявки — всё доступно. Поля «отметка андеррайтера» для нового документа не существуют — утечка из будущего, нельзя |
| Разметка | Для сканов — ручная разметка полей андеррайтерами по гайдлайну, с оценкой согласованности (κ). Для структурированных выгрузок эталон уже есть |
| Смещение отбора | Меньше, чем у флагмана: поток документов — все кредитные заявки, а не отобранные правилами. Но сканы плохого качества могут быть недопредставлены в разметке — нужен целевой сбор |
| Репрезентативность | Поток кредитных заявок.<br><br>Разные типы и форматы документов. Редкие форматы (фото с телефона, старые шаблоны бухгалтерии) — собирать специально |
| Объём | Поток кредитных заявок (меньше, чем операций: заявок тысячи в год, не миллионы). Для обучения извлечения из сканов — нужны тысячи размеченных документов |
| Качество | Форматы разнородные (Excel, PDF-скан, фото). Скан плохого качества — отдельный сценарий, не низкое качество данных. Пропуски, противоречия между документами |
| Право на использование | Банковская тайна + ПДн (фин. показатели заёмщика, представители, поручители). Размещение и обработка сканов с ПДн — вопросы комплаенсу/DPO/юристам: основания, обезличивание, регион хранения. Вердикт — не архитектора |
| Разрыв и план устранения | Эталон для сканов — ручная разметка, которой нет. План: гайдлайн по полям, разметка контрольной выборки сканов андеррайтерами, оценка согласованности. Для структурированных выгрузок эталон есть |

**Вердикт по готовности данных:**

- **Для пилота — Pilot-ready:** на структурированных выгрузках/Excel (эталон есть) можно начинать сразу и замерять эффект. Сканы добавляются параллельно по мере разметки.
- **Для целевого прода — Gap с планом:** для сканов и фото нужен размеченный набор (которого нет) и гайдлайн. План закрытия — разметка ~тысяч сканов андеррайтерами, оценка κ, горизонт — недели/месяцы. До этого сканы идут на ручной ввод или фолбэк.

Не **Blocked**: эталон для значительной доли документов (структурированные выгрузки) есть. Не **Ready**: для сканов эталона нет.

## Раздел 5. Эксперимент (план пилота)

### Какие неопределённости проверяет пилот

1. Какую долю полей модель извлекает с высокой уверенностью (идут в карточку без подтверждения) на реальных документах разных типов.
2. Сколько времени андеррайтер реально экономит на заявку vs текущие 1,5 ч.
3. Как часто модель галлюцинирует (додумывает поля, которых нет) и как это ловит валидатор формата.
4. Как ведёт себя на сканах плохого качества и фото с телефона.

### Приёмочный набор

Выборка документов разных типов и форматов (Excel, PDF-скан, фото с телефона), стратифицированная по типу документа, качеству скана, формату. Для структурированных — готовый эталон; для сканов — ручная разметка андеррайтеров. Объём — порядка нескольких сотен документов для диагностического отсева, затем тысячи для приёмочного прогона (точное число — на пилоте, объём определяют через пилот).

### Метрики и пороги

- F1 по полям (отдельно по критичным и некритичным) — порог из доли ручной правки, которую готов принять андеррайтер.
- Доля документов без ручной правки — порог = заметная экономия времени.
- Критичные поля, попавшие в карточку без подтверждения, — таких быть не должно, порог нулевой.
- Источник порогов — экономия времени андеррайтера и цена неверного кредитного решения, не публичный рейтинг модели.

### Что означает провал на сценарии

- Низкий F1 по критичным полям → эти поля всегда на подтверждение, модель не пускаем в автозаполнение.
- Галлюцинация (додуманное поле, которого нет) → валидатор формата должен ловить; если не ловит → усиливаем валидатор или откат для этого типа.
- Скан плохого качества → фолбэк на ручной ввод или отдельный конвейер для таких документов.

### При каком результате решение меняется

- Экономия времени на заявку ниже расчётной вдвое → пересматриваем конвейер (цена/размещение), либо честно закрываем.
- Хотя бы одно критичное поле попало в карточку без подтверждения → откат, guardrail нарушен.
- F1 по критичным полям ниже порога на размеченной выборке → модель не подходит, переводим критичные поля на ручной ввод, ML оставляем только для некритичных.
