# Задание 3. Архитектура AI-сервиса

Все три сервиса собраны по одному принципу: модель отвечает за то звено, где действительно нужна выученная закономерность, остальное считает обычный код, а действие, которое почувствует клиент, подтверждает человек — тот же, что и сегодня участвует в процессе.

## Как устроен флагман

Модель ставит операции оценку подозрительности, пороговые правила продолжают помечать операции параллельно, валидатор не пускает в очередь сломанный ответ, а сотрудник финмониторинга разбирает, эскалирует, отказывает или снимает пометку. Платёж сервис не трогает вовсе.

Операции приходят через шину событий и обрабатываются микробатчами: так читать шину дешевле, чем по одной записи, а задержка остаётся в пределах секунд. Платёж ответа не ждёт, потому что сервис стоит сбоку от платёжного пути. Поиск по документам, инструменты и агент не подключены — маршрут известен заранее, признаки считает обычный код.

Контрольную выборку для оценки качества берём из всего потока, а не из того, что подняла модель, иначе мы измерим сами себя.

## Две другие инициативы

**Документы заявки.** Сначала модель распознаёт скан, потом вторая модель находит в тексте нужные поля, а суммы и даты сверяет обычный код. Критичные поля подтверждает андеррайтер, он же принимает решение по кредиту. Документу, который прислал клиент, система не доверяет.

**Отток.** Пакетный пересчёт агрегатов даёт список на обзвон, звонит персональный менеджер. Автоматических писем и предложений клиенту сервис не отправляет.
