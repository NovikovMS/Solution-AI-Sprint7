# Дополнительное задание. Поиск причин деградации модели

Разбор просадки `precision@N` после выхода банка в сегмент селлеров маркетплейсов.

## Артефакты

| Файл | Содержание |
|---|---|
| `diagnosis.md` | Три возможные картины просадки, девять конкурирующих гипотез по трём уровням, семь различающих экспериментов с порядком запуска |
| `architecture_fix.md` | Разбор, почему сигнал мониторинга не сработал, новые сигналы с порогами, группа как объект конфигурации, регрессионный набор, выкатка и откат |
| `diagrams/` | C4 Component для сервиса приоритизации после правки: новые компоненты выделены цветом |
| `ADR_1.md` | Версия v1.1: что пересматриваем в v0.3 и v1.0, решение, цена, отклонённые варианты |

## Выводы

**Средняя метрика не говорит, что произошло.** Просадка `precision@N` описывает три разных события: сегмент ранжируется плохо, сегмент вытесняет остальных из top-N при корректной оценке, либо причина не в сегменте и совпала с ним по времени. Решения у них разные, поэтому разбивка по сегментам — первое действие, а не уточнение.

**Вытеснение не требует ошибки модели.** Очередь вмещает те же 10 тысяч разборов в месяц. Если модель добросовестно ставит новому сегменту высокие оценки, потому что его профиль не похож на обучающую выборку, места в top-N занимает он.

**Вытеснение не видно по precision.** У пострадавших сегментов в top-N пробиваются только сильнейшие кандидаты, поэтому доля подтверждений среди них не падает, а может вырасти. Потеря измеряется `recall@N` на контрольной выборке и составом top-N по группам.

**Половина гипотез лежит вне модели:**

- несчитающиеся признаки;
- отставание от шины;
- формальный разбор;
- изменившаяся базовая ставка.

Различаются они запросами к журналу. Переобучение не нужно, новая разметка нужна в одном эксперименте из семи.

**Сценарий был предусмотрен, а механизм не сработал.** В плане мониторинга из задания 3 есть строка про появление сегмента, которого не было в обучении. Подвела не формулировка, а классификация под ней: **новый сегмент целиком ушёл в класс «прочее».** Такая корзина есть у всякой классификации по справочнику, и вредит она дважды:

- **в кодировании признаков стирает новизну.** Незнакомый ОКВЭД приходит в модель не как ошибка, а как валидная категория, которая в обучении означала «мелкая редкая отрасль». Модель видит знакомый вход и не имеет повода усомниться;
- **в отчётности создаёт иллюзию полного покрытия.** Пропусков нет, разбивка по сегментам формально выполняется. Но класс, куда падает всё новое, — единственный, чья метрика бессмысленна по построению: он смешивает несвязанные вещи, и вывод «просело на прочем» ничего не подсказывает.

Сюда же третье, более общее упущение: **за распределением потока по классам вообще не следили.** Мониторинг смотрел на качество внутри классов, но не на то, как меняются их доли в генеральной совокупности. Сдвиг состава потока — самостоятельное событие, наступающее раньше любой просадки качества, и наблюдать его дёшево: разметка не нужна, нужны только доли. Его не отследили, поэтому и причину не расследовали вовремя.

Отсюда два требования к архитектуре: **у класса «прочее» сигналом служит размер** — качество мы измеряем везде, но здесь оно ничего не сообщает, а доля класса в потоке сообщает; и **у сервиса должно быть определённое поведение на классе, которого он не знает** — по умолчанию, а не по решению человека, заметившего рост.

**Группа становится объектом конфигурации.** Три состояния:

- **карантин** — оценка не пишется, порядок за правилами. Назначается по умолчанию;
- **тень** — оценка считается и пишется в журнал, очередь не меняет;
- **боевой** — оценка участвует в порядке очереди.

Новая группа не ранжируется, пока по ней не размечена контрольная выборка. Откат тоже становится групповым: сегмент возвращается на правила, остальной поток продолжает работать с моделью.
